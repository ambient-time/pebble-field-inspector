# Independent review: Pebble 2 settings-wipe incident

Read-only review of enclosed evidence only. Full wipe remains unreproduced. Owner trigger, model, and firmware are unknown.

---

## (1) Ranked findings

**F1 — Concrete defect: recursive `next_snapshot` stack growth (released PBW)**  
**Source:** released binary behavior; host harness; Diorite disassembly; corrected `src/c/main.c` `next_snapshot` (loop at ~154–232).  
**Confidence:** High (defect); **Low** as cause of settings wipe / setup return.  
Empty or sparse batches recursed (~232 B/frame, ~20 stages). Emulator: released PBW exits on capture (incl. battery-only); corrected PBW completes. Install/launch does not collect sensors, so this alone does not explain install-only wipe. PC/LR=0 fault line is weak symbolication; recursion is established independently.

**F2 — Concrete platform behavior: BlobDB clear on first connect / `isUnfaithful`**  
**Source:** `BlobDB.init` (`BlobDB.kt` ~267–279); `BlobDatabase` enum (`GenerateRoomEntity.kt`); `TransportConnector.doAfterConnection` (~273–279).  
**Confidence:** High (behavior); **Low–medium** as incident cause.  
When `unfaithful || !previouslyConnected`, sends `ClearCommand` for every DB with `sendClear == true` (App, AppConfigs, HealthParams, etc.). **WatchPrefs opts out** (`sendClear = false`). This is database re-sync from the companion, **not** `ResetMessage.FactoryReset` / factory reset (`Reset.kt`, `SystemService.factoryReset`, fw_reset distinction in upstream). Can erase app records/configs and health params and feel like “settings wiped”; it does not by itself prove return-to-setup / full wipe.

**F3 — Concrete non-call: Signal Station install path does not factory-reset**  
**Source:** `AndroidSignalStation.installWatchApp` (~302–327): `sideloadApp(..., loadOnWatch = false)` then `launchWatch`; no `factoryReset`. Factory reset only behind explicit debug UI (per investigation; not contradicted by excerpts).  
**Confidence:** High for source intent; cannot prove which packets the owner’s installed build sent.

**F4 — Evidence-supported hypothesis: companion removal stopped sync/recovery interference**  
**Source:** owner report; `AndroidSignalStation` watch collect (~103–108) does not reinstall on reconnect; `BlobDB.init` / recovery classification / `WatchOnboardingScreen` auto-FW on PRF (~179–200); `FirmwareUpdater.maybeAutoResume` (conditional).  
**Confidence:** Medium that uninstall halted connection-driven work; **Low** that a specific mechanism “restored” erased settings. Report cannot separate stop-clear/stop-PRF-update vs coincidental recovery.

**F5 — Unconfirmed lead: launch before locker sync**  
**Source:** `installWatchApp` + `Locker.sideloadApp` (`loadOnWatch = false` skips wait-for-sync launch path ~262–277); `waitUntilAppSyncedToWatch` exists but is not used here.  
**Confidence:** Code race possible; **Low** causal. Emulator run: app-entry ack preceded launch; race not seen; still only putbytes app/exec+resources.

**F6 — Speculation: physical firmware/transport fault or true factory reset path**  
Unknown owner FW; emulator is SDK Diorite v4.3 `0e3c3fd` (2016), no recovery slot. Upstream reset endpoint distinguishes factory vs normal/PRF. **Cannot exclude** device-specific fault. No incident packet log.

**Challenge to existing write-up:** Stack fix and “don’t equate BlobDB clear with factory reset” are right. The write-up still under-weights the gap between **app crash → system watchface** and **erased settings + setup**. Treating companion uninstall as recovery evidence is weak without pre/post watch state. Installer race is over-elevated relative to F1/F2. No excerpt gap was treated as a defect.

## (2) Emulator comparison: proves / does not prove

**Proves**
- Released APK + released PBW: native capture can fault/exit watchapp; phone may wait; repeatable with logging.
- Same APK + corrected PBW only: battery capture succeeds; watch stays on result UI (~80% battery).
- Fresh pair path: DB sync completed; connection held.
- Relay: **127** phone→watch packets; **0** reset endpoint; **0** FW/recovery transfers; installs = object types 0x85/0x84 only (3 each).
- Full wipe **not** reproduced; proposed install/launch race **not** reproduced in that run.
- Released crash is consistent with recursive collector, not with reset packets in this harness.

**Does not prove**
- Owner’s physical model/FW, BLE pair semantics, or recovery-updater path (socket/PRF exemptions; no recovery slot).
- That capture or install caused settings wipe / setup UI.
- That BlobDB clear did or did not run on the owner’s watch (`isUnfaithful` / first connect unknown).
- That uninstall restored data vs merely stopped further companion behavior.
- Serial shim `SS-EMU-00001` only unblocked selection; not evidence about the real watch identity.

## (3) Safest next 3 isolated tests

1. **Static map (no device):** For each `BlobDatabase` with `sendClear=true` vs WatchPrefs/phone store, list user-visible “settings” and onboarding flags. Separates F2 cosmetic wipe from factory setup.
2. **Emulator-only first-connect/unfaithful harness:** Drive `BlobDB.init` clear+repopulate on Diorite; screenshot apps/configs/health/prefs and whether UI resembles setup—no hardware, no owner watch.
3. **Passive owner facts only:** Firmware string, approximate order (pair → install → launch → capture → symptoms), and whether “setup” was pairing/onboarding vs app missing—**no reinstall, no sideload, no log extraction that requires reset.**

Avoid: physical reinstall, recovery experiments on the recovered watch, repeating the paused install path.

---

## (4) Companion architecture / first-pair sync — relevant risk?

**Yes, as a residual platform risk; not proven root cause.**

`TransportConnector` always inits BlobDB after normal-mode negotiate; `BlobDB.init` **clears** sendClear DBs when unfaithful or not previously connected, then repopulates from **this** phone. First Signal Station pair can coincide with that path. Effects: app locker/config/health-param loss and confusing UX; **not** equivalent to factory reset or reset-endpoint wipe. WatchPrefs is protected from clear. Recovery auto-update and FW auto-resume are separate, gated paths; relevant after a fault, not evidenced here.

Uninstall stopping those workflows matches owner belief without proving causality. Signal Station’s install API is a thin sideload/launch client on top of that stack.

---

## (5) Release recommendation

- **Keep** public settings-wipe warning and install pause; do **not** republish  
  `3809a2c0…` / lab 8 pairing as “safe.”
- **Ship blocker for any new build:** corrected non-recursive collector (F1), **new** watch version (not dev 1.3.0 / `24031842…`), rebuilt APK with matching provenance, full existing JS/C/regression pack green, six-target SDK build.
- **Do not** lift the wipe warning solely because F1 is fixed or emulator wipe failed—owner-class wipe is **unreproduced** and F2 remains a first-pair behavior users can misread as wipe.
- Optional before unpause: short public note that companion first-pair/unfaithful sync clears selected BlobDBs (not factory reset); document WatchPrefs exemption.
- No replacement binary from this investigation alone; no physical reinstall for acceptance.

## Missing evidence

Owner watch model/FW; exact sideload/launch/capture order; incident BLE/logs; whether `isUnfaithful`/first companion connect; what “setup” meant UI-wise; any reset-endpoint traffic on device; confirmation Android companion (vs other app) was removed; post-incident watch DB contents. Emulator FW ≠ owner FW.

**Bottom line:** One high-confidence ship-stopping watchapp crash (F1). One high-confidence non-factory clear-on-first-sync behavior (F2). Owner full wipe/setup return **unexplained and unreproduced**. Fix F1 for any future artifact; keep pause/warning until wipe class is scoped or clearly attributed and communicated.
